Why a PASS Should Not Travel

AI assurance 的核心錯誤之一，是讓上游測試結果自動替下游系統背書。

核心命題

Model PASS ≠ Integration PASS ≠ Deployment PASS ≠ Operational Safety PASS.

這不是說前一層評測沒有價值，而是說每個 PASS 都有自己的 scope。測試模型本身，與測試模型接上檢索、工具、權限和工作流程之後的整體系統，是不同的驗證對象；而實驗環境中的整合測試，又與真實部署中的持續行為不同。

一條較完整的 assurance chain

Model evaluation → Integration validation → Deployment monitoring → Incident feedback → Regression replay

Model evaluation 回答模型在指定測試條件下的能力與失效；Integration validation 檢查 RAG、工具、agent、權限與 workflow 接上之後，整體是否仍符合驗收條件；Deployment monitoring 處理真實使用者、資料、時間與環境變動；Incident feedback 把事故變成可定位證據；Regression replay 則檢查同一個失敗是否能在新版本或新供應商上被重新驗證。

PASS 的正確語義

一個 PASS 應該被理解成：「在這個 target、這組條件、這套 acceptance criteria 與這個時間點，證據足以支持這個有限結論。」

它不應該被理解成：「這個系統接下來在任何部署層都可以被視為安全。」因此，上游證據可以支援下游測試設計，卻不能取代下游自己的證據。

兩個常見錯誤

第一，supplier evidence substitution。 Model card、benchmark 或供應商 evaluation 可以作為輸入，但不能替代使用方對真實部署的驗證。

第二，single-cause attribution。 如果模型版本、prompt、RAG、data 與 tool configuration 同時改動，重新執行後的差異不能只歸因給模型。可重跑不只要求保留輸入，也要求保留足以重建測試條件的 provenance。

為什麼這與 portability 有關

若 assurance 只存在於供應商的測試報告中，切換供應商時，使用方的驗證能力很容易歸零。若事故被保存成自己的 replayable corpus，新的模型就必須重新面對同一批真實世界問題。

因此，跨層不可傳遞性不是純粹的測試哲學；它直接決定企業能不能把 deployment evidence 變成長期、可攜的治理資產。
